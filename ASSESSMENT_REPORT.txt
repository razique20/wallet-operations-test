STAGE 2: INITIAL INVESTIGATION & LIVE REPRODUCTION OF VULNERABILITIES
--------------------------------------------------------------------------------
[x] 2.1. Empty UI State Diagnosis
     - Opened http://localhost:5173. Observed table headers with no rows.
     - Cause: Database seeds initial wallet balances ($100 for User 1, $250 for User 2)
       without creating any initial transaction records.

[x] 2.2. Live Reproduction of Critical Vulnerabilities
     - Bug 1 (Duplicate Crediting / Replay Attack):
       Submitted `0xgood` deposit twice. Both succeeded, crediting 50 USDT twice!
       The UI displayed "0xgood" TWICE in the ledger. This proved lack of replay
       protection.
     - Bug 2 (Concurrency Race Condition):
       Identified that `/withdraw` checked balance in Python without row-level locks.
       Concurrent withdrawals would cause double-spend / overdraft.
     - Bug 3 (Insecure Direct Object Reference - IDOR):
       `GET /transactions/{id}` did not verify ownership. Any user could access
       any other user's private financial records by guessing the ID.
     - Bug 4 (AI Data Leak & Reference Exposure):
       `POST /ai/ask` allowed passing arbitrary `user_id`, letting callers inspect
       other users' transactions, and passed raw reference codes to external LLMs.
     - Bug 5 (Zero Crypto Validation):
       `POST /deposits/verify` accepted fake tokens, wrong recipient addresses,
       unconfirmed transactions, and mismatched amounts.

STAGE 3: CODE MODIFICATIONS & ENGINEERING IMPROVEMENTS
--------------------------------------------------------------------------------
[x] 3.1. Financial Concurrency & Negative Balance Prevention (`backend/app/main.py`)
     - Implemented database-level pessimistic locking (`with_for_update()`) on
       `Wallet` row inside atomic transaction.
     - Added database CheckConstraint `balance >= 0` on `wallets` table in `models.py`.
     - Result: Race conditions between concurrent withdrawals are completely eliminated.
       Exactly one request succeeds; the subsequent request detects insufficient funds.

[x] 3.2. Idempotency & Replay Attack Defense (`backend/app/main.py`)
     - Added withdrawal idempotency: checks if `reference` has already been executed
       for this user. If already completed, returns 200 with `idempotent: true`
       without deducting balance again.
     - Added global deposit replay protection: checks if `tx_hash` was already claimed
       by any wallet in the system. Re-claiming by another user returns HTTP 409 Conflict.

[x] 3.3. Simulated Crypto Deposit Policy Enforcement (`backend/app/main.py`)
     - Network Check: Strictly accepts only `ethereum`.
     - Token Check: Strictly accepts only `USDT` (rejects `0xwrongtoken` with HTTP 400).
     - Recipient Check: Strictly accepts only `0xmerchant` (rejects `0xwrongaddress` with HTTP 400).
     - Confirmations Check: Strictly requires $\ge 12$ block confirmations
       (rejects `0xunconfirmed` with HTTP 400).
     - On-Chain Status: Strictly checks `success == True` (rejects `0xfailed` with HTTP 400).
     - Exact Amount Match: Verifies requested deposit amount matches on-chain transfer
       amount using exact `Decimal` precision.
     - RPC Outage Resiliency: Caught `ConnectionError` on provider lookup and returns
       HTTP 503 Service Unavailable with friendly error, preventing server crashes.

[x] 3.4. Authorization Enforcement & IDOR Fix (`backend/app/main.py`)
     - `GET /transactions/{transaction_id}`: Checks `t.user_id == caller`.
       Returns HTTP 404 if transaction belongs to another user, preventing IDOR enumeration.
     - `POST /ai/ask`: Disallows overriding `user_id` from request body. Strictly binds
       context to authenticated caller (`user_id = current_user`).

[x] 3.5. AI Privacy Guardrails & Reliability (`backend/app/main.py`)
     - Privacy Redaction: Stripped internal reference hashes and transaction IDs from
       the LLM prompt context to protect user secrets.
     - Timeout Protection: Handled `MockLLM` timeout (`TimeoutError`) returning HTTP 504
       Gateway Timeout rather than unhandled 500 error.
     - In-Memory Response Caching: Added query caching keyed by `(user_id, question, last_tx_id)`
       to avoid redundant provider calls for unchanged transaction history.

[x] 3.6. PostgreSQL Scalability & Pagination (`backend/app/main.py`, `models.py`)
     - Added compound database indexes:
       * `ix_transactions_user_id_id_desc` on `(user_id, id)`
       * `ix_transactions_user_id_created_at_desc` on `(user_id, created_at)`
       * `ix_transactions_reference` on `(reference)`
     - Implemented bounded limit and offset pagination (`limit: int = 50, offset: int = 0`)
       preventing memory exhaustion on large 10M-row datasets.

[x] 3.7. Frontend Overhaul (`frontend/src/main.tsx`)
     - Real-Time Balance Header: Live display of user's current wallet balance.

     - Status Indicators & Badges: Clean badges for `COMPLETED` (green), `PENDING` (amber),
